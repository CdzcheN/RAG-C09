# 接口契约（课题 C09）

> 负责人：A。本文是三人并行开发的**唯一接口事实来源**：字段定义只在这里写，其他文档一律链接过来。
> 任何字段新增/改名/改语义都属于**破坏性变更**，必须走 §5 的变更流程。

## 1. 契约的基本原则

1. **单一来源**：所有结构体的权威定义在 `src/common/schema.py`（dataclass），本文档与代码必须逐字一致；
2. **冻结优先**：接口在 W1 内冻结并广播（见 [`项目启动与实施指南.md`](项目启动与实施指南.md) §3.1 的 G1 门禁）；冻结后 B/C 才能并行开工，冻结前用**假数据桩**顶替；
3. **不确定就不加字段**：宁可先用 `extra: dict` 暂存探索性字段，也不要在契约里塞未定型的列；
4. **可追溯**：每条产物都要能回答"哪份配置、哪个种子、哪次运行产生的"（见 §4 的元信息要求）。

## 2. 四类数据对象

数据流：**样本 → 预测 → 特征 → 指标**。四类对象各自落盘，互不覆盖，便于单独重跑某一段。

```
challenge_set.jsonl / normal_set.jsonl      ← A 构造（Sample）
        │
        ▼  B 跑管道
predictions/<exp_id>.jsonl                  ← B 产出（Prediction）
        │
        ▼  B 提特征
features/<exp_id>.parquet                   ← B 产出（FeatureRow，一行一样本）
        │
        ▼  C 训练+评估
metrics/<exp_id>.json + figures/*.png       ← C 产出（MetricRecord）
```

### 2.1 `Sample`（数据集样本，A 产出）

| 字段 | 类型 | 含义 | 取值域 |
|---|---|---|---|
| `sample_id` | str | 全局唯一 ID | `"{source}-{split}-{index:05d}-{challenge_type}"`，如 `hotpotqa-dev-00427-retrieval_failure` |
| `schema_version` | str | 契约版本 | 当前 `"1.0"` |
| `source` | str | 数据来源 | `"squad"` \| `"hotpotqa"` |
| `split` | str | 集合类型 | `"normal"` \| `"challenge"` |
| `challenge_type` | str | 挑战类型 | `"none"` \| `"retrieval_failure"` \| `"evidence_conflict"` \| `"outdated"` |
| `question` | str | 问题（构造后） | — |
| `gold_answer` | str | 真值答案（构造后，可判定真伪） | — |
| `gold_context` | list[str] | 支撑证据句（构造后） | 至少 1 句 |
| `passages_for_retrieval` | list[dict] | 交给检索器的候选段落 `{title, text}` | 挑战样本中被污染/替换后的版本 |
| `is_hallucination` | int | 标签：在该样本下模型回答是否属于幻觉 | 0/1，**由构造参数自动推导**（见 [`数据构造规范.md`](数据构造规范.md) §3） |
| `construct_params` | dict | 构造参数字典（算子类型、替换强度、随机种子等） | 见 `数据构造规范.md` §4 |
| `provenance` | dict | 溯源：原始数据集标识、`revision`、原始行索引 | 用于回溯原始样本 |

### 2.2 `Prediction`（模型输出，B 产出）

| 字段 | 类型 | 含义 |
|---|---|---|
| `sample_id` | str | 外键，指向 `Sample` |
| `exp_id` | str | 本次运行 ID（见 §3 命名） |
| `answer` | str | 生成模型给出的答案 |
| `passages` | list[dict] | 检索结果 `{rank: int, title: str, text: str, score: float}` |
| `prompt` | str | 实际送入模型的提示（截断后），用于人工复核 |
| `baseline_confidence` | float | 自制置信度基线：模型自评"该答案正确"的概率 ∈ [0,1] |
| `decode` | dict | 解码参数 `{do_sample: bool, max_new_tokens: int, temperature: float}` |
| `latency_ms` | float | 单条推理耗时（含检索） |

### 2.3 `FeatureRow`（特征，B 产出，一行一样本）

特征列名**固定**，新增列需走变更流程。所有列均为数值型，缺失用 `NaN` 并在报告中说明。

| 列名 | 含义 | 主要来源 |
|---|---|---|
| `sample_id` | 主键 | — |
| `exp_id` | 运行 ID | — |
| `challenge_type` | 挑战类型（评估分组用） | `Sample` |
| `is_hallucination` | 标签 | `Sample` |
| `entailment_max` | 答案←证据 蕴含概率的最大值（NLI 交叉编码器） | 特征模块 |
| `entailment_mean` | 蕴含概率均值（跨证据句） | 特征模块 |
| `contradiction_max` | 矛盾概率最大值 | 特征模块 |
| `overlap_em` | 答案与证据的精确匹配（0/1） | 特征模块 |
| `overlap_f1` | 答案与证据的 token-F1 | 特征模块 |
| `citation_cov` | 证据句覆盖率：答案中的命名实体/关键词被证据支持的比例 | 特征模块 |
| `conflict_count` | 证据之间互相矛盾的句对数 | 特征模块 |
| `retrieval_top_score` | 检索最高分（BM25 或稠密分数） | 检索模块 |
| `answer_len` | 答案 token 数 | 管道 |
| `baseline_confidence` | 自评置信度基线（对照用，**不参与主方法特征**） | 管道 |

> 纪律：对照组（自评置信度）与实验组（一致性特征）在评估时严格分开，不得把 `baseline_confidence` 混入实验组特征表，否则无法论证"一致性特征相对基线的增益"。

### 2.4 `MetricRecord`（评估结果，C 产出）

`results/metrics/<exp_id>.json`，字段：

| 字段 | 类型 | 含义 |
|---|---|---|
| `exp_id` / `seed` / `stage` | str/int/str | 运行标识（`stage` ∈ W1…W6） |
| `model` | str | 生成模型与判别器标识，如 `"qwen2.5-0.5b+logreg"` |
| `split` | str | 评估集合：`normal` \| `challenge` \| `challenge:<type>` |
| `n_samples` | int | 样本数（含正负样本数） |
| `auc` / `pr_auc` | float | 主指标（正类 = 幻觉） |
| `precision` / `recall` / `f1_macro` / `f1_micro` | float | 阈值下的分类指标（阈值同记录在 `threshold`） |
| `confusion` | dict | `{tp, fp, tn, fn}` |
| `threshold` | float | 判定阈值（默认 0.5，另存校准后的最优阈值） |
| `latency_ms_mean` | float | 效率指标 |
| `config_hash` | str | 配置文件哈希 |
| `env_report` | str | 环境指纹路径（`results/env_report.json`） |
| `timestamp` / `notes` | str | 时间与备注 |

汇总（三种子）另存 `results/metrics/summary.csv`：每行 = (方法, 集合)，列含 `auc_mean`、`auc_std`、`p_value_t`、`p_value_wilcoxon`。

## 3. 目录与命名

```
data/processed/    challenge_set.jsonl, normal_set.jsonl, construct_log.json        ← A
configs/           default.yaml, models.yaml, challenge.yaml, detect.yaml           ← 全组
results/
├── predictions/   <exp_id>.jsonl        ← B
├── features/      <exp_id>.parquet      ← B
├── metrics/       <exp_id>.json, summary.csv   ← C
├── figures/       <name>.png            ← C（脚本可重绘）
├── logs/          <exp_id>.log          ← 全组
└── env_report.json                      ← 各人自跑
```

`exp_id` 命名：`{stage}-{method}-{seed}`，全小写、连字符分隔，例如 `w4-consistency-logreg-13`、`w2-baseline-selfconf-42`。

规则：
- **一份产物一份文件**，不覆盖旧结果；重跑生成新 `exp_id`（可在后缀加 `-r2`）；
- **产物必须可重建**：给定 `exp_id` + 配置 + 种子，任何人能重跑出同一文件（浮点数值允许逐位差异，指标须落在 std 内）；
- 大文件（`predictions/*.jsonl`、`features/*.parquet`）体积若 >50 MB，改为压缩 `.jsonl.gz` / 保留 parquet 的列裁剪（只存 `FeatureRow` 必需列）。

## 4. 产物的元信息要求

每个 `predictions/*.jsonl` 的**首行**为元信息行（`{"_meta": {...}}`），包含：

`exp_id`、`schema_version`、`seed`、`config_hash`、`model`（含 revision/本地路径）、`dataset_revision`（HuggingFace 数据集版本）、`env_report`、`timestamp`、`git_commit`（若在协作仓库提交）。

理由：报告中的每个数字都要能追到"哪份配置、哪个种子、哪个数据集版本"。缺少元信息行的产物视为不合格，需重跑。

## 5. 契约变更流程

```
① 提案（任意成员）→ 在周会提出：字段名、类型、含义、影响范围
② 全组确认（A 主持）→ 确认无冲突后由 A 修改 src/common/schema.py 与本文档
③ 同步下游（B/C）→ 改各自读写代码；接口相关假数据桩一并更新
④ 小样本回归（20 条冒烟）→ 通过后方可继续批量实验；旧的 exp_id 结果保留但标注 schema 版本
```

禁止事项：
- 禁止在各自模块里"就地改名"或私自新增列（会导致 B/C 的产物无法对接）；
- 禁止把探索性字段写进契约（先放 `extra: dict`，验证有价值后再提案转正）。

## 6. 产物校验（约定规则，脚本见 `src/common/validate.py`）

| 校验项 | 规则 |
|---|---|
| 必需字段 | §2 各表的"必需"字段齐全，无多余未登记列 |
| 主键唯一 | `sample_id` 在单个产物内唯一 |
| 外键完整 | `Prediction.sample_id` ⊆ `Sample.sample_id` |
| 取值域 | `challenge_type`、`split`、`is_hallucination ∈ {0,1}` 合法 |
| 数值范围 | 概率类字段 ∈ [0,1]；`latency_ms` > 0 |
| 缺失率 | 任一特征列缺失率 >20% 需在周会说明 |
| 元信息 | 首行 `_meta` 存在且字段齐全（§4） |

校验不通过即视为该次运行失败，修复后重启，不进入后续评估。
